# Использование AI при выполнении задания

## Инструменты и запросы

Использовался Codex desktop: анализ DOCX через OOXML, поиск и чтение официальной документации, генерация и редактирование Go/YAML/JSON/Python/Bash, запуск команд и разбор результатов. Точное название модели в доступном контексте не указано; не приписываю ей неподтверждённую версию. Автономные подагенты не использовались.

Основные пользовательские запросы:

- «изучи документацию и составь план выполнения» — изучение исходного задания, проверка среды и согласование объёма.
- «первый варинат но с возможным расширением до всех допов» — обязательная часть плюс deploy-all и Chaos Testing, Galera отдельным этапом.
- «Go (Recommended)», «Два сценария (Recommended)», «Через UI (Recommended)» — язык Dagger, два вида отказа и ручное создание администратора Kuma.
- «PLEASE IMPLEMENT THIS PLAN» с согласованным планом — реализация и локальная проверка.

AI подготовил Compose-слои, Go-модуль Dagger, контроллер Docker/API, конфигурации экспортёров, Prometheus rules, Grafana dashboard, тесты, README и упаковку. Решения проверялись реальным Docker, Prometheus/Grafana API и тестами, а не только выводами модели.

## Обнаруженные и исправленные ошибки

### 1. Docker kill не подтвердил автоматический restart

Согласованный AI-план предполагал, что `docker kill --signal=SIGKILL` проверит restart-policy. В Docker Engine 29.8.1 после команды Kuma оставалась `exited`, exit code 137, `RestartCount=0`, хотя политика была `unless-stopped`. Сценарий stop/start до этого успешно показал красный и зелёный статус.

Проблема выявлена запуском Chaos Testing, `docker inspect` и событиями Docker. Аварийный сценарий заменён на прямой SIGKILL init-процессу из временного контейнера с host PID namespace и единственной дополнительной capability KILL. Так Docker не получает ручную команду остановки, а тест требует фактического роста RestartCount. Исправление также внесено в README. Обработчик отмены неуспешного теста восстановил остановленную Kuma.

### 2. Неверный тег cAdvisor

Первоначально AI указал `ghcr.io/google/cadvisor:0.53.0`, затем предположил `v0.55.1`. Registry ответил `manifest unknown` в обоих случаях. Документация разных релизов использует разные соглашения о префиксе `v`; копирование примера без проверки оказалось ненадёжным.

Проверены официальный GitHub Releases API и `docker manifest inspect ghcr.io/google/cadvisor:0.60.6`. Зафиксирован существующий multi-architecture образ 0.60.6. Полный deploy затем прошёл, включая реальные контейнерные CPU/RAM-метрики. [Официальные релизы](https://github.com/google/cadvisor/releases).

### 3. Принудительная очистка мешала восстановлению после отмены

Первый shell cleanup в Dagger выполнял только `docker rm -f` контроллера. При отмене это могло уничтожить процесс Go раньше выполнения deferred восстановления сервиса после Chaos Testing.

При ревью цепочки сигналов обнаружено, что одного `defer` внутри Go недостаточно, если внешний процесс немедленно уничтожает контейнер. Перед удалением добавлен штатный `docker stop` с запасом времени 210 секунд. Go получает SIGTERM, отменяет основной контекст и выполняет восстановление в отдельном контексте. Ограничение при аварийном завершении всего Docker/хоста явно описано в README.

### 4. Старое значение up могло скрыть потерю обновлений

Первое выражение здоровья наблюдаемости считало `count(up == 1)` без проверки возраста. При прекращении обновлений успешные серии могут оставаться видимыми в lookback-окне Prometheus; одного значения 1 недостаточно для подтверждения текущей доступности.

Выражение изменено: учитываются только серии моложе 20 секунд, отсутствие результата явно преобразуется в 0. Для Kuma/MariaDB также проверяется timestamp. Добавлены promtool-тесты здоровых сервисов, отказа, отсутствующих и устаревших метрик; статусные панели используют instant query и не подменяют отсутствие данных предыдущим зелёным значением.

### 5. Контекст Dagger зависел от расположения Git

Первоначальный `defaultPath="/"` для исходников работал в основном репозитории, но при проверке распакованного архива Dagger выбрал контекст `/tmp` вместо каталога проекта и попытался прочитать посторонний `snap-private-tmp`, завершившись permission denied. Это обнаружено именно запуском из архива после удаления контейнеров с сохранением данных, а не статической проверкой Compose.

Значение заменено на `defaultPath="."`, которое разрешается относительно модуля. Через функцию source entries проверено содержимое, затем повторный deploy-all из распакованного архива без `.git` самого проекта прошёл. В логе Host.directory указывает на каталог распакованного проекта. Чужие каталоги и секреты не включаются в передаваемые исходники.

## Границы результата

Galera не реализована: это согласованное расширение, а не выполненный бонус. Создание администратора и мониторов Kuma остаётся операцией через UI. Пароли и рабочие volumes не входят в архив. Итоги фактических проверок фиксируются в `docs/VALIDATION.md`; неподтверждённые платформы и ручные сценарии не объявляются проверенными.
