## 2026-11-04 — MariaDB и Uptime Kuma

**Запрос:** «начнем с основного слоя приложения, мария бд + кума в компос файле. провреь по официальной документации совместимость и способ подключения. не забудь про персистентное хранение и проверки готовности.»

**Решение:** `compose.app.yaml` с Kuma 2.5.9 и MariaDB 11.4.13, отдельным пользователем БД, файловыми secrets, томами `/var/lib/mysql` и `/app/data`. MariaDB доступна внутри Compose-сети, Kuma — на `127.0.0.1:3001`. Запуск Kuma ожидает готовности БД. Добавлены README и исключения секретов из Git.

**Основания:** [документация Kuma](https://github.com/louislam/uptime-kuma/wiki/Environment-Variables) подтверждает внешнюю MariaDB с v2 и параметры подключения; [MariaDB](https://mariadb.com/docs/server/server-management/automated-mariadb-deployment-and-administration/docker-and-mariadb/using-healthcheck-sh) описывает штатную проверку готовности. Матрица совместимости конкретных версий в изученных источниках не найдена; выбранная пара проверена запуском.

**Проблемы и меры:**

- [Встроенная проверка Kuma](https://raw.githubusercontent.com/louislam/uptime-kuma/2.5.9/extra/healthcheck.go) не проверяет HTTP-статус. В Compose задана проверка с допуском только 200/302; доступность SQL она не подтверждает.
- В логах миграций появилось предупреждение об implicit commit DDL. Миграции завершились, схема проверена; предупреждение в upstream не исправлялось.
- Доступ к Docker-сокету из песочницы был запрещён; получено разрешение на выполнение команд, права сокета не менялись.

**Проверки:** Compose-конфигурация валидна; `up --wait` успешен, оба сервиса `healthy`. SQL из контейнера Kuma подтвердил MariaDB 11.4.13, пользователя приложения и 28 таблиц. Маркеры в БД и `/app/data` сохранились после `down` и повторного `up`, затем удалены. HTTP вернул 302. Файлы паролей исключены из Git; `git diff --check` без ошибок.

**Осталось:** создать администратора и проверить пользовательский сценарий с монитором. Приложение оставлено работающим; Dagger и мониторинг ещё не реализованы. Ошибочных предложений AI на этом этапе не зафиксировано.

## 2026-11-04 — Слой мониторинга

**Запрос:** «подготовь компос для прометеуса и графаны. нужны метрики ресурсов, хоста, контейнеров, состояния бд, доступности и времени ответа uptime kuma. так же как и в предыдущем данные должны хрнаиться постоянно и так же напиши хэлфчеки. dagger и дашборд оставь на след этап.»

**Решение:** отдельный Compose с Prometheus, Grafana, Node Exporter, cAdvisor, mysqld_exporter и Blackbox Exporter; healthcheck у каждого сервиса. История Prometheus и БД Grafana — в именованных томах. Добавлены конфигурации сбора и скрипт создания отдельного пользователя БД; пароли — в локальных secrets. Настройки сверены с официальными источниками, ссылки приведены в README.

**Ошибки первоначальной конфигурации AI и исправления:**

- mysqld_exporter с рекомендованными upstream правами выдавал `Access denied ... SLAVE MONITOR`: стандартный коллектор пытался читать статус репликации MariaDB 11.4. Для одиночной ноды отключён ненужный `slave_status`; после пересоздания проверены логи и сбор метрик.
- Node Exporter сообщал, что `/run/udev/data` отсутствует. Указан путь к udev хоста через уже смонтированный корень; после перезапуска ошибка больше не наблюдалась.

**Проверки:** `promtool` и Compose приняли конфигурации; все 6 сервисов `healthy`, 6 целей Prometheus — `UP`. Проверены `mysql_up=1`, успешная HTTP-проба Kuma, её длительность, CPU/RAM обоих контейнеров. Число CPU, объём RAM и размер корневой ФС из метрик совпали с хостом. После `down`/`up` сохранились историческая точка Prometheus и временно изменённая настройка Grafana; исходная настройка восстановлена. Повторный запуск скрипта подготовки успешен. Dagger, источник данных и дашборд Grafana оставлены на следующий этап.

## 2026-11-04 — Три обязательные команды Dagger

**Запрос:** «теперь на go реализуй 3 основные команды, но без допа.»

**Решение:** Go-модуль Dagger v0.21.11 с `deploy-app`, `deploy-monitoring`, `configure-grafana`; сокет Docker проброшен через `WithUnixSocket`. Помощник на хостовом Docker монтирует проект по исходному абсолютному пути, чтобы Compose правильно находил конфигурации и secrets. Обёртка подставляет путь и сокет. Отключены кэши функций и повторное использование слоя с действиями развёртывания. Через Grafana API применяются источник Prometheus и дашборд из 13 панелей с постоянными UID. Бонусные команды не добавлялись.

**Проблемы и меры:** в Docker CLI-образе отсутствуют Bash и OpenSSL — скрипт подготовки адаптирован под POSIX sh, пароли генерируются из `/dev/urandom`. При одном вызове Dagger произошёл TLS-таймаут Docker Hub; повторный вызов успешен без изменения кода.

**Проверки:** все три команды выполнены через Dagger на существующем стенде. Запросы всех 13 панелей вернули данные через API Grafana; повторный `configure-grafana` сохранил ID источника и дашборда без дубликатов. Подготовка паролей отдельно проверена в пустом временном каталоге: права 0600, повторный запуск не меняет значения. Значения паролей не найдены в проверенных логах вызовов. Проверки синтаксиса shell и `git diff --check` успешны. README обновлён.

## 2026-11-04 — Chaos testing

**Запрос:** «Реализуй второе задание Chaos Testing. Добавь команду Dagger `chaos-test` с выбором цели `mariadb` или `uptime-kuma`».

**Решение:** команда с проверкой исходной готовности, таймаутами и попыткой восстановления при сбое. Статус проверяется по выражению сохранённой панели Grafana и свежим метрикам через её API. По документации Docker ручной stop подавляет restart-policy: поэтому stop API → два сбора со статусом 0 → явный start → статус 1 проверяются отдельно от SIGKILL основного процесса → автоматического перезапуска с увеличением RestartCount. Называть явный start автоматическим восстановлением было бы неверно.

**Проверки:** оба варианта команды прошли на стенде; данные панелей изменились `1 → 0 → 1`, затем подтверждён автоматический перезапуск после завершения процесса. Все 8 сервисов после тестов `healthy`. Четыре unit-теста проверили cleanup, сохранение причин ошибок, защиту нездоровой цели и отклонение старой метрики. Недопустимая цель отклонена с кодом 1. `git diff --check` успешен. Скриншоты дашборда не проверялись; README содержит инструкцию ручного наблюдения.

## 2026-11-06 — Проверка полноты deploy-all

**Запрос (кратко):** предложить проверку цепочки «сервис → экспортёр → Prometheus → Grafana» после развёртывания.

**Ошибка AI и обнаружение:** при ревью сгенерированного `DeployAll` и вызываемых скриптов выявлена неполная реализация бонусного требования: готовность контейнеров и применение Grafana-конфигурации проверяются, но успешный сбор метрик и данные панелей не валидируются. Успех команды не гарантирует исправность всей цепочки.

**Предложение:** добавить финальный этап с ограниченным ожиданием: проверить состав и доступность шести целей Prometheus, свежие `mysql_up=1` и `probe_success=1`, затем выполнить запросы сохранённых панелей через Grafana с проверкой ожидаемых рядов CPU/RAM хоста и обоих контейнеров. При сбое возвращать ненулевой код и конкретную причину.

**Исправление:** в `deploy-all` добавлен четвёртый этап `validate-platform` с общим таймаутом 120 секунд. Он проверяет точный состав целей, `up=1`, возраст исходных образцов до 30 секунд, доступность БД/Kuma и запросы всех 13 сохранённых панелей через Grafana. Для CPU/RAM обязательны ряды обоих контейнеров; пустые и нечисловые результаты отклоняются. README дополнен.

**Проверки:** полный `deploy-all` на существующем стенде завершился успешно, включая этап 4/4. Девять новых unit-тестов проверили запросы панелей, подмену цели, старые метрики, `mysql_up=0`, отсутствие контейнера, неверный источник, ошибку запроса, пустые/NaN/Inf-результаты и прерывание долгой проверки общим таймаутом. Вместе с четырьмя прежними тестами — 13 успешных; `git diff --check` без ошибок. Отказы моделировались в тестах, сервисы для них не останавливались; запуск с пустыми томами не проверялся.
